From **Carter, respawn/pocket 430808 (2026-09-01)** — web session-viewer UX (web is the reference; iOS mirrors once the web lands each). Web owners noted; iOS parity is forge's to track.

- **C1 · Per-message share + link-grants-access** — a share control on each MESSAGE (not just the session). A shared link, on the recipient's login, grants THAT person access to the session; a public session grants automatically; links may need to be minted per-recipient. · web: relay (extends `SessionShareControl` / #498) + backend auth for the grant-on-login. · iOS: per-message share sheet + the same access-grant model. · **status: backlog (web-first).**
- **C2 · Share draft title** — prefill the share text with a title, e.g. "working on senti pocket…" / "join my senti pocket session." · web: relay. · iOS: same. · **status: backlog.**
- **C3 · Real platform icons in the share sheet** — show the ACTUAL platform icons (SMS/WhatsApp/email/…), not a paper-airplane for all. · web: relay (#498 share sheet). · iOS: native share sheet already does this. · **status: backlog.**
- **C4 · Header-over-chat + tabs** — the header (session name etc.) pinned on top of the chat at ALL times; consolidate everything under it into TABS; clear chat↔header separation. (Carter couldn't see it yet — atlas confirmed it's built in #500, not shipped.) · web: warden #500 layout redesign. · iOS: mirror the header+tabs pattern. · **status: web in-flight (#500).**
- **C7 · In-app pending-invites + collaboration model** (Carter 430868) — invites are discoverable IN the app, not only via the email link: signing into the account whose email the invite was sent to and opening **Sessions** shows **pending invites** there; accept → (a) the inviter gets a notification email + in-app "so-and-so joined", (b) the inviter's session/seat count +1, (c) the pending clears, (d) the shared session appears in their list. Plus a **glanceable owner / collaborator / admin badge** per session (friction-free, minimal). Because the pending list is **keyed to the account's email**, "the invite isn't here → you're in the wrong account" — it self-diagnoses the multiplayer-invite P0 (email-bound accept mismatch). · web: relay (Sessions/invite UX) + backend (pending list, accept notifications, idempotent seat-count). · iOS: mirror — a pending-invites section + the ownership badge in the sessions list. · **status: web-first (also a P0 UX fix); iOS mirrors.**
- **C5 · Borderless floating composer + roomier chat** (Carter 430836) — the composer floats over the chat (transparent bg, input text stays legible); **the borders of the composer are the ONLY delimiter — drop the separator line between composer and feed** (redundant); and the chat pane + composer should be **noticeably wider/roomier** on desktop. · web: warden/relay layout. · iOS: mirror the borderless floating composer + generous chat width. · **status: web iterating; iOS mirror.**
- **C6 · Overlay stacking discipline** (Carter 430836) — floating/overlay elements must render ABOVE content and never occlude controls: the Share modal opened BEHIND the chat (partially visible, transparent = z-index/backdrop-filter containing-block trap); on mobile the floating "who's active" header hid the "load older" control. iOS lesson: any sheet/popover/floating header sits above the feed and never covers an actionable control. · web: warden/relay. · iOS: apply to sheets + the floating presence header. · **status: web bug (warden's lane); iOS design rule captured.**
- **C8 · Dark theme — the "declared but never wired" trap** (from sentinelayer-web #525, relay, 2026-09-03) — the web app *looked* like it supported dark mode and did not. Relay's measurement: `darkMode: ["class"]` present in the tailwind config, **77** `dark:` variants across components, **nothing anywhere that sets the `dark` class**, and no dark palette to switch to. So every one of those 77 variants was unreachable styling that read as "done" in the source. · web: relay #525 (adds the palette + the thing that actually sets the class). · **iOS lesson, which is the reason this is captured rather than just noted:** the phone has the identical trap — a `.dark` variant in an asset catalog, or `preferredColorScheme` branches, are inert unless something exercises them, and they look implemented in a diff. **Verify a theme by rendering in it, not by grepping for its variants.** · iOS: sharpens **B11** (light/dark parity) — the parity check must be a render, not a token audit. · **status: web in-flight (#525); iOS captured.** src: pocket 431117
- **C9 · Scroll-to-reply lands NEAR the message, not ON it — the vacuous stability check** (Carter 431025; root-caused by relay in sentinelayer-web #526, 2026-09-03) — the web alignment loop had a 30-frame budget to let the list settle and **consumed about 2 of them**, because its settle test compared a value against itself: `parent.scrollTo({top, behavior:"auto"})` applies **synchronously**, so reading `parent.scrollTop` on the very next line returns what was just written and `drift` is ~0 **by construction** (non-zero only when the browser clamps). "Stable for two consecutive frames" was therefore true immediately, the loop exited while the rows above the target were still being measured, they settled, the target slid, and the reader landed near their message. · web: relay #526 — settling now requires BOTH that the scroll took effect AND that **the target held still between frames** (the half that actually observes relayout), extracted as `alignmentSettled` so it is testable without a DOM; plus a target past max offset counts as settled once the container is pinned. · **iOS lesson, identical trap:** `setContentOffset(_:animated:false)` and `scrollToItem` apply immediately, so reading `contentOffset` right after confirms only your own write — and in SwiftUI `ScrollViewReader.scrollTo` before layout has settled has the same shape. **A settle check must observe something the writer did not just set: the TARGET's position across two frames, not the container's offset.** · iOS: applies to any scroll-to-message/reply/anchor work (feeds B1/B2/B7). · **status: web in-flight (#526); iOS design rule captured before the phone feed is built.** src: pocket 431122

- **C10 · Mobile composer — the shipped web layout is now the concrete iOS reference** (Carter 430713; verified in live code by relay, 2026-09-03) — Carter asked for the ChatGPT composer behaviour on mobile and it landed; this captures the *measured* result so the phone copies a real spec rather than a description. · web: `globals.css:400`, `@media (max-width: 639px)` — grid areas `"header header header"` / `"primary primary primary"` / `"leading footer trailing"`, i.e. **the textarea spans the full width on its own row and the controls sit BELOW it, bottom-aligned**; `max-height: max(30svh, 5rem)`; auto-grows from `rows={1}` via `scrollHeight`; send is an **ArrowUp** glyph, attach a **+**. · **iOS target:** the compose view in `apps/SentiPocketApp` — full-width `TextEditor`/`UITextView` that grows to a `max(30% of screen height, 5rem)` ceiling, with the +/↑ controls on a row beneath it rather than inline trailing. Note `svh` is the *small* viewport unit — on iOS the equivalent must exclude the keyboard inset, so measure against the **keyboard-adjusted** safe area, not the full screen. · **status: web SHIPPED; iOS backlog.** Sharpens **C5** (borderless floating composer) with the actual geometry. src: pocket 431318
- **C11 · Overlay visibility must be SCOPED, not just stacked — the other half of C6** (relay, verified in live code 2026-09-03) — the web's floating chat launcher is `position: fixed; bottom: 24px; right: 24px; z-index: 400` (`styles/chat.css:25-28`) and is suppressed on exactly one route (`App.tsx:264`, `/admin`). **So it renders on top of every session page and covers the Agents tab.** · **Why this is a separate rule from C6 and not a repeat:** C6 captured an overlay that was too LOW (the Share modal rendered *behind* the chat). This is the mirror image — an overlay that is high enough but **never asks whether it should be present at all**. Suppressing by naming the one route where it hurts is an allowlist-by-exception: every screen added later inherits the bubble by default, and the failure is silent because the bubble looks correct in isolation. · **iOS lesson:** any app-shell-level floating control (FAB, presence pill, call banner) needs **two** independent answers — *what does it stack above* **and** *on which screens does it exist* — and the second should be an opt-IN per screen, not an opt-out list. It must also clear the tab bar and the home indicator, since a `bottom: 24px` equivalent lands on top of both. · web: relay offered to take the fix. · iOS: applies to the phone's call banner + any future compose FAB. · **status: web bug open; iOS design rule captured.** src: pocket 431318
- **C12 · The ticket board belongs INSIDE the session, scoped to it — not a global dashboard list** (Carter 431497, 2026-09-04) — verbatim: *"I see the board but it's in dashboard. It should be in sessions or near there — how the hell does someone find it straight from the session they're in? I asked to be in tabs. Also when you put it outside and it has any sessions in it that's confusing. Each session should have their own."* **Three distinct asks, and they are separable:** (a) **placement** — reachable from within the session you are in, not a sibling destination you must navigate away to; (b) **tabs** — Carter asked for this twice now, and it is the same request as C4's header+tabs consolidation, so the ticket board is a TAB of the session, not a page; (c) **scoping** — a board that aggregates tickets across sessions is confusing *because the ticket only means something relative to a session*; each session shows its own. · web: relay (`TicketsSection.tsx`, currently under `dashboard/`). · **iOS implication, and it is a data-model point rather than a layout one:** the phone must not build a global ticket list and then filter it — **the fetch itself should be session-scoped**, because a global-then-filter design makes (c) a rendering concern that will leak back the moment a second surface consumes it. Same reasoning as C7's pending-invites being keyed to the account: **scope at the source, not at the view.** · iOS target: session-detail tab alongside the feed, once the phone has a session view (feeds B1/B2/B7). · **status: web-first (relay); iOS mirrors.** src: pocket 431497
